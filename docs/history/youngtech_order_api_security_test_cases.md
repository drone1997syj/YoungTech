# 영테크 홈페이지 1 — 주문 생성 API 보안 테스트 지시서

## 0. 테스트 목적

영테크 홈페이지 1의 `/api/orders` 주문 생성 금액 검증 수정이 제대로 되었는지 테스트한다.

이번 테스트의 목적은 단순히 주문이 성공하는지 확인하는 것이 아니다.

핵심 목적은 프론트에서 가격, 총액, 수량, 상품 상태를 조작했을 때 서버가 안전하게 차단하는지 확인하는 것이다.

---

## 1. 반드시 확인해야 할 핵심 원칙

이번 테스트에서 확인해야 할 원칙은 다음과 같다.

```text
1. 정상 주문은 성공해야 한다.
2. 가격 조작 주문은 실패해야 한다.
3. 총액 조작 주문은 실패해야 한다.
4. 재고 초과 주문은 실패해야 한다.
5. 품절/비활성/삭제 상품 주문은 실패해야 한다.
6. 실패한 주문은 DB에 저장되지 않아야 한다.
7. 실패한 주문은 재고를 차감하지 않아야 한다.
8. 성공한 주문은 서버 계산 금액으로만 저장되어야 한다.
```

---

## 2. 사전 확인

현재 `server/index.js` 전체 `node --check`가 기존 dirty change의 중복 선언 문제 때문에 실패한다고 보고되었다.

따라서 테스트 전에 아래 사항을 먼저 확인한다.

| 방법 | 설명 |
|---|---|
| A안 | 기존 문법 문제를 먼저 정리한 뒤 전체 서버 실행 테스트 |
| B안 | 기존 문법 문제가 주문 API와 무관하고 서버가 실제 실행 가능하다면, 주문 API 실제 호출 테스트부터 진행 |

단, 서버가 실행되지 않으면 API 테스트는 의미가 없다.

최소한 `/api/orders`가 실제 호출 가능한 상태인지 확인해야 한다.

---

## 3. 테스트 대상

주요 테스트 대상 API는 다음과 같다.

```text
POST /api/orders
```

관련 파일은 다음과 같다.

```text
server/index.js
src/components/MockPGModal.jsx
src/context/ShopContext.jsx
src/pages/Checkout.jsx
server/db.js
```

이번 테스트에서는 특히 `server/index.js`의 `/api/orders`가 아래 원칙을 지키는지 검증한다.

```text
프론트 가격을 믿지 않는다.
프론트 총액을 믿지 않는다.
서버가 products 테이블에서 가격을 다시 조회한다.
서버가 최종 주문금액을 다시 계산한다.
서버가 재고를 검증한다.
서버가 품절/비활성/삭제 상품을 차단한다.
실패한 주문은 주문 저장, 재고 차감, 매출 반영이 없어야 한다.
```

---

## 4. 테스트 전 준비 데이터 확인

테스트 전에 DB에서 테스트 가능한 상품을 3개 이상 확인하거나 만든다.

| 테스트 상품 | 조건 |
|---|---|
| 정상 상품 A | `is_active = true`, `is_deleted = false`, `stock >= 5`, 가격 정상 |
| 재고 부족 상품 B | `stock = 1` 또는 낮은 재고 |
| 품절 상품 C | `stock = 0` |
| 비활성 상품 D | `is_active = false` |
| 삭제 상품 E | `is_deleted = true` |

가능하면 실제 운영 상품을 망가뜨리지 말고, 테스트용 상품을 사용한다.

테스트 전 각 상품의 아래 값을 기록한다.

```md
## 테스트 전 상품 상태

| 상품ID | 상품명 | 가격 | 재고 | is_active | is_deleted |
|---|---|---:|---:|---|---|
```

---

## 5. 인증 준비

`/api/orders`는 `authenticateToken`이 적용되어 있으므로 로그인 토큰이 필요하다.

테스트용 회원으로 로그인해서 Bearer token을 확보한다.

보고서에는 토큰 원문을 절대 쓰지 말고, 아래처럼만 표시한다.

```text
인증 토큰 확보: 성공
테스트 사용자 ID: OOO
```

# 6. 필수 테스트 케이스

## TC-01. 정상 상품 1개 주문

### 목적

정상 요청은 성공해야 한다.

### 요청 조건

```text
정상 상품 A
quantity = 1
프론트 total_amount = 서버 계산값과 동일
```

### 기대 결과

| 항목 | 기대 결과 |
|---|---|
| API 응답 | 성공 |
| 주문 생성 | 생성됨 |
| orders.total_amount | 서버 계산 금액 |
| orders.order_items | DB 상품명/DB 가격/검증된 수량 |
| 재고 | 1개 차감 |
| 매출 반영 | 서버 계산 금액 기준 |

---

## TC-02. 정상 상품 여러 개 주문

### 목적

여러 상품 주문 시 합계가 서버 기준으로 계산되는지 확인한다.

### 요청 조건

```text
정상 상품 A quantity = 2
정상 상품 B quantity = 1
프론트 total_amount = 서버 계산값과 동일
```

### 기대 결과

| 항목 | 기대 결과 |
|---|---|
| API 응답 | 성공 |
| 상품별 subtotal | DB 가격 × 수량 |
| 최종 total_amount | 서버 계산 상품 합계 + 서버 배송비 |
| 재고 | 각 상품 수량만큼 차감 |

---

## TC-03. 프론트 상품 가격 조작

### 목적

브라우저, localStorage, request 조작으로 상품 가격을 낮춰도 서버가 막는지 확인한다.

### 요청 조건

```text
정상 상품 A
quantity = 1
order_items.price = 1
total_amount = 1
```

### 기대 결과

둘 중 하나여야 한다.

| 허용 가능한 결과 | 설명 |
|---|---|
| 주문 실패 | 프론트 총액과 서버 총액 불일치로 차단 |
| 서버 금액으로만 저장 | 프론트 price를 무시하고 서버 DB 가격으로 저장 |

현재 지시서에서는 “금액 불일치 시 실패”가 더 안전하다고 했으므로, 가장 좋은 기대 결과는 주문 실패다.

### 반드시 확인할 것

| 항목 | 기대 결과 |
|---|---|
| 주문 생성 | 생성되지 않아야 함 |
| 재고 차감 | 차감되지 않아야 함 |
| 매출 반영 | 반영되지 않아야 함 |
| 에러 메시지 | 금액 불일치 또는 주문 금액 검증 실패 |

## TC-14. 중복 상품 ID 요청

### 목적

같은 상품 ID가 두 번 들어왔을 때 안전하게 처리되는지 확인한다.

### 요청 조건

```json
[
  { "id": "상품A", "quantity": 1 },
  { "id": "상품A", "quantity": 2 }
]
```

### 기대 결과

아래 둘 중 하나로 일관되게 처리되어야 한다.

| 처리 방식 | 설명 |
|---|---|
| 합산 처리 | 상품A quantity = 3으로 합산 후 검증 |
| 오류 처리 | 중복 상품 ID 요청으로 실패 |

어느 방식이든 프론트 가격을 믿으면 안 되고, 재고 검증은 최종 수량 기준이어야 한다.

## TC-16. 주문 실패 시 트랜잭션 롤백 확인

### 목적

여러 상품 중 하나가 실패하면 전체 주문이 실패하고, 일부 재고만 차감되는 일이 없는지 확인한다.

### 요청 조건

```text
정상 상품 A quantity = 1
재고 부족 상품 B quantity = 재고 초과
```

### 기대 결과

| 항목 | 기대 결과 |
|---|---|
| API 응답 | 실패 |
| 주문 생성 | 생성되지 않음 |
| 정상 상품 A 재고 | 차감되지 않아야 함 |
| 상품 B 재고 | 차감되지 않아야 함 |
| 매출 반영 | 없어야 함 |

이 테스트는 매우 중요하다.

부분 성공이 나면 안 된다.

현재 정책상 금액 불일치 시 실패 처리라면, 주문 실패가 가장 안전하다.

## TC-18. 정상 주문 후 DB 저장값 확인

### 목적

성공 주문이 서버 기준으로 저장되는지 DB에서 직접 확인한다.

### 확인 방식

주문 성공 후 `orders`에서 해당 주문을 조회한다.

확인 항목:

| 항목 | 기대 결과 |
|---|---|
| `orders.total_amount` | 서버 계산 최종 금액 |
| `orders.order_items` | 서버 재구성 JSON |
| JSON 상품명 | DB 상품명 |
| JSON 가격 | DB 상품 가격 |
| JSON 수량 | 검증된 수량 |
| JSON subtotal | DB 가격 × 수량 |

## 8. 추가 주의사항

테스트 중 실제 상품 데이터가 손상되지 않도록 가능하면 테스트 상품과 테스트 계정을 사용한다.

정상 주문 테스트로 재고가 차감되면, 테스트 후 원래 재고로 복구하거나 테스트 결과에 차감 사실을 기록한다.

주문 실패 테스트에서 주문 레코드, 재고 차감, 매출 반영이 발생하면 아직 안전하지 않은 상태로 본다.

## 9. 특히 중요한 테스트

특히 가장 중요한 테스트는 아래 5개다.

```text
TC-03 프론트 상품 가격 조작
TC-04 프론트 total_amount 조작
TC-09 재고보다 많은 수량 주문
TC-16 주문 실패 시 트랜잭션 롤백 확인
TC-18 정상 주문 후 DB 저장값 확인
```

이 중 하나라도 실패하면 실제 PG 연동 전에 반드시 수정해야 한다.

## 10. 합격 기준 요약

| 확인 항목 | 합격 기준 |
|---|---|
| 가격 1원 조작 | 주문 실패 또는 서버 가격으로 저장 |
| 총액 1원 조작 | 주문 실패 |
| 재고 초과 주문 | 주문 실패 |
| 실패 주문 | DB에 주문 생성 안 됨 |
| 실패 주문 | 재고 차감 안 됨 |
| 성공 주문 | `orders.total_amount`가 서버 계산값 |
| 성공 주문 | `orders.order_items.price`가 DB 가격 |
| 트랜잭션 | 일부 상품만 재고 차감되는 현상 없음 |
