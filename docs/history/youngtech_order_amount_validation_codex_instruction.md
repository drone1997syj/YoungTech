# 영테크 홈페이지 1 — 주문 생성 금액 검증 보완 지시문

## 0. 작업 목적

영테크 홈페이지 1의 주문 생성 금액 검증 로직을 보완한다.

이전 점검 결과에 따르면 현재 `/api/orders`는 프론트에서 전달된 `total_amount`, `order_items.price`, `order_items.name`을 거의 그대로 사용하고 있고, 서버에서 DB 기준으로 상품 가격과 총액을 다시 계산하지 않는 문제가 있다.

이번 작업의 목표는 **실제 PG 연동 전에 주문 생성 API를 안전하게 만드는 것**이다.

아직 실제 PG 연동이나 `payments` 테이블까지 확장하지 말고, 우선 `/api/orders`에서 다음 항목만 보완한다.

- 서버 기준 금액 검증
- 상품 검증
- 수량 검증
- 재고 검증
- 안전한 재고 차감
- 서버 기준 주문 상품 JSON 저장
- 서버 기준 주문 총액 저장

---

## 1. 현재 문제 요약

현재 구조는 다음과 같은 위험이 있다.

| 항목 | 현재 문제 | 위험도 |
|---|---|---|
| 상품 가격 | 프론트 `order_items.price`를 그대로 저장 | 높음 |
| 주문 총액 | 프론트 `total_amount`를 그대로 `orders.total_amount`에 저장 | 높음 |
| 상품명 | 프론트 `order_items.name`을 그대로 저장 | 중간 |
| 서버 가격 재조회 | 주문 생성 시 DB `products.price` 재조회 없음 | 높음 |
| 총액 재계산 | 서버에서 상품 합계/배송비/최종금액 재계산 없음 | 높음 |
| 수량 검증 | 정수, 1 이상, 최대 수량 검증 부족 | 높음 |
| 재고 검증 | 재고보다 많은 주문 차단 부족 | 높음 |
| 재고 차감 | `GREATEST(stock - quantity, 0)` 방식이라 초과 주문도 성공 가능 | 높음 |
| 품절/비활성/삭제 상품 | 주문 생성 시 차단 부족 | 높음 |
| 매출 반영 | analytics/revenue가 프론트 총액 기준일 수 있음 | 높음 |

## 2. 이번 수정 목표

이번 작업의 핵심 원칙은 아래와 같다.

```text
프론트 값 = 고객이 주문하고 싶다고 보낸 희망 목록
서버 DB 값 = 실제 주문 가능 여부, 상품 가격, 재고, 최종 주문 금액의 기준
```

즉 프론트에서 받은 값 중 신뢰해도 되는 것은 최소한으로 제한한다.

---

## 3. 프론트에서 받아도 되는 값

프론트 요청에서 다음 값은 받을 수 있다.

```text
productId 또는 id
quantity
selectedOptionId 또는 optionId가 있다면 옵션 식별자
address
payment_method
tax_document_type
delivery_request 등 주문 부가 정보
```

하지만 이 값들도 서버에서 기본 검증은 해야 한다.

---

## 4. 프론트에서 받아도 신뢰하면 안 되는 값

아래 값들은 프론트에서 넘어와도 주문 계산 기준으로 사용하면 안 된다.

```text
상품명 name
상품 가격 price
상품 합계 subtotal
배송비 shippingFee
최종 주문금액 total_amount
할인금액 discountAmount
```

프론트가 위 값을 보내더라도 서버 계산 기준으로 사용하지 말고, 필요하다면 비교용 또는 로그용으로만 사용한다.

## 6. `/api/orders`에서 반드시 구현해야 할 검증

`/api/orders` 주문 생성 시 아래 순서로 처리한다.

### 6.1 요청값 기본 검증

다음을 확인한다.

| 검증 항목 | 기준 |
|---|---|
| 로그인 사용자 | `authenticateToken` 유지 |
| `order_items` 존재 여부 | 배열이고 1개 이상이어야 함 |
| 상품 ID | 유효한 값이어야 함 |
| 수량 | 정수여야 함 |
| 최소 수량 | 1 이상이어야 함 |
| 최대 수량 | 비정상적으로 큰 수량 차단. 예: 상품당 최대 999개 또는 합리적 상한 |
| 중복 상품 | 같은 상품 ID가 여러 번 오면 수량을 합산하거나 오류 처리 |
| 주소 | 기존 필수값 검증 유지 |

---

### 6.2 상품 정보 서버 재조회

프론트 `order_items`에 들어 있는 `id/productId`를 기준으로 DB에서 상품 정보를 다시 조회한다.

서버에서 다시 조회해야 하는 값:

| 서버 재조회 항목 | 이유 |
|---|---|
| 상품 ID | 실제 존재 여부 확인 |
| 상품명 | 프론트 조작 방지 |
| 현재 판매가 | 가격 조작 방지 |
| 재고 | 초과 주문 방지 |
| 활성 여부 `is_active` | 비공개 상품 주문 방지 |
| 삭제 여부 `is_deleted` | 삭제 상품 주문 방지 |

현재 프로젝트 DB가 SQLite 계열이면 `SELECT ... FOR UPDATE`는 맞지 않을 수 있다.

따라서 DB가 SQLite라면 `FOR UPDATE`를 억지로 쓰지 말고, 트랜잭션 안에서 검증 후 조건부 재고 차감 방식으로 처리한다.

---

### 6.3 판매 가능 상품 검증

각 상품에 대해 아래 조건을 확인한다.

| 조건 | 실패 시 처리 |
|---|---|
| 상품이 존재해야 함 | 주문 생성 실패 |
| `is_deleted`가 false여야 함 | 주문 생성 실패 |
| `is_active`가 true여야 함 | 주문 생성 실패 |
| 재고가 0보다 커야 함 | 주문 생성 실패 |
| 재고가 주문 수량 이상이어야 함 | 주문 생성 실패 |
| 가격이 정상 숫자여야 함 | 주문 생성 실패 |

실패 시에는 어떤 상품 때문에 실패했는지 알 수 있도록 명확한 에러 메시지를 반환한다.

예시:

```text
상품 재고가 부족합니다: 미쓰비시 서보모터 HG-KR43
판매 중지된 상품입니다: OOO
삭제되었거나 존재하지 않는 상품입니다.
```

## 7. 서버 기준 주문 상품 재구성

프론트에서 받은 `order_items`를 그대로 저장하지 말고, 서버가 DB에서 조회한 값으로 새 주문 상품 목록을 만든다.

예시 구조:

```js
const serverOrderItems = [
  {
    id: product.id,
    name: product.name,
    price: product.price,
    quantity: requestedQuantity,
    subtotal: product.price * requestedQuantity
  }
];
```

중요한 점:

```text
name은 DB 상품명 사용
price는 DB 상품 가격 사용
quantity는 검증된 요청 수량 사용
subtotal은 서버에서 계산
```

현재 DB에 별도 `order_items` 테이블이 없고 `orders.order_items JSON`을 쓰고 있으므로, 이번 1차 수정에서는 기존 구조를 유지해도 된다.

다만 JSON에 저장되는 내용은 반드시 서버 재구성 결과여야 한다.

---

## 8. 서버 기준 금액 재계산

서버에서 아래 값을 직접 계산한다.

| 항목 | 계산 기준 |
|---|---|
| 상품 합계 `subtotal` | DB 상품 가격 × 검증된 수량 |
| 배송비 `shippingFee` | 서버 배송비 정책 |
| 최종 주문금액 `totalAmount` | 상품 합계 + 배송비 - 서버 기준 할인금액 |
| 주문 상품별 합계 | 상품별 DB 가격 × 수량 |

프론트에서 넘어온 `total_amount`는 저장 기준으로 사용하지 않는다.

다만 디버깅과 보안 확인을 위해 필요하다면 다음처럼 비교는 가능하다.

```text
client_total_amount = 프론트가 보낸 금액
server_total_amount = 서버가 재계산한 금액
```

두 값이 다르면 주문을 막거나, 최소한 경고 로그를 남긴다.

운영 결제 전 구조로는 **불일치 시 주문 생성 실패**가 더 안전하다.

---

## 9. 배송비 계산

현재 프론트 `Checkout.jsx`에서 배송비를 계산하고 있더라도, 서버에서도 동일한 배송비 정책을 다시 적용해야 한다.

예시 정책이 현재 명확하지 않다면 기존 프론트 정책을 확인해서 서버로 옮긴다.

예시:

```text
상품 합계 50,000원 이상 무료배송
그 미만 배송비 3,000원
```

또는 현재 프로젝트에서 사용 중인 배송비 정책이 다르면 그 정책을 서버에 반영한다.

중요한 것은 `shippingFee`도 프론트 값을 믿지 않는다는 점이다.

## 10. 재고 차감 로직 수정

현재처럼 아래 방식이면 안 된다.

```sql
stock = GREATEST(stock - quantity, 0)
```

이 방식은 재고가 부족해도 주문이 성공하고 재고만 0으로 만들 수 있다.

대신 다음 중 하나로 수정한다.

### 10.1 권장 방식 A: 트랜잭션 안에서 검증 후 차감

```text
1. 트랜잭션 시작
2. 상품 정보 조회
3. 재고 >= 주문수량 검증
4. 주문 생성
5. 재고 차감
6. 차감 결과 확인
7. 트랜잭션 커밋
```

### 10.2 권장 방식 B: 조건부 UPDATE

```sql
UPDATE products
SET stock = stock - ?
WHERE id = ?
  AND stock >= ?
  AND is_active = TRUE
  AND is_deleted = FALSE
```

그리고 UPDATE 결과 변경된 row 수가 1인지 확인한다.

변경된 row 수가 0이면 재고 부족 또는 판매 불가 상품이므로 주문을 실패 처리하고 트랜잭션을 롤백해야 한다.

SQLite를 사용 중이라면 DB 문법에 맞게 `TRUE/FALSE` 표현을 조정한다.

## 11. 트랜잭션 처리

주문 생성, 주문 상품 JSON 저장, 재고 차감, 매출 반영은 하나의 트랜잭션으로 묶는다.

중간에 하나라도 실패하면 전체 롤백되어야 한다.

트랜잭션 안에서 처리할 것:

```text
1. 요청값 검증
2. 상품 DB 조회
3. 서버 기준 금액 계산
4. 주문 생성
5. 재고 차감
6. analytics/revenue 반영이 있다면 서버 계산 금액 기준으로 반영
```

실패 시:

```text
주문 생성 안 됨
재고 차감 안 됨
매출 반영 안 됨
```

## 12. 주문 저장 기준

`orders.total_amount`에는 반드시 서버가 재계산한 최종 금액만 저장한다.

`orders.order_items` JSON에는 프론트 원본이 아니라 서버에서 재구성한 상품 목록을 저장한다.

저장 기준:

| 저장 필드 | 저장해야 할 값 |
|---|---|
| `orders.total_amount` | 서버 재계산 최종 금액 |
| `orders.order_items` | 서버 DB 기준으로 재구성한 주문 상품 JSON |
| 상품명 | DB 상품명 |
| 상품 가격 | DB 상품 가격 |
| 수량 | 검증된 수량 |
| 배송비 | 서버 계산 배송비 |
| 매출/정산 기준 금액 | 서버 재계산 금액 |

## 13. 프론트 수정 방향

프론트는 크게 바꾸지 않아도 된다.

다만 아래 원칙을 지킨다.

| 프론트 영역 | 수정 방향 |
|---|---|
| `Checkout.jsx` | 현재 합계/배송비 표시는 UI 용도로 유지 가능 |
| `MockPGModal.jsx` | 주문 요청에 가격/총액을 보내더라도 서버는 신뢰하지 않도록 처리 |
| `ShopContext.jsx createOrder()` | 가능하면 `id/productId`, `quantity` 중심으로 요청 구조를 단순화 |
| 주문 완료 화면 | 서버 응답의 최종 주문금액을 기준으로 표시 |

현재 Mock PG 구조에서는 프론트 결제창에 표시되는 금액과 서버 최종 주문금액이 달라질 수 있으므로, 서버에서 계산한 최종 금액을 응답으로 내려주고 프론트가 이를 표시하도록 정리하면 좋다.

다만 이번 작업에서 프론트를 과하게 갈아엎지는 말고, 서버 방어를 우선한다.

---

## 14. 실제 PG 연동은 이번 작업 범위에서 제외

이번 작업에서는 실제 PG 연동까지 하지 않는다.

이번 작업 범위:

```text
/api/orders 주문 생성 금액 검증
상품 가격 서버 재조회
수량 검증
재고 검증
서버 기준 총액 재계산
안전한 재고 차감
orders 저장값 정리
```

이번 작업 범위 아님:

```text
실제 PG 결제 연동
payments 테이블 생성
paymentKey 저장
PG webhook 처리
PG 승인 검증
PG 취소/환불
refunds 테이블 생성
```

실제 PG는 다음 단계에서 별도 작업으로 진행할 예정이다.

## 15. 수정 후 테스트할 시나리오

수정 후 아래 테스트를 반드시 진행한다.

| 번호 | 테스트 | 기대 결과 |

| 7 | 수량을 소수로 요청 | 주문 실패 |
| 8 | 재고보다 많은 수량 주문 | 주문 실패 |
| 9 | 품절 상품 주문 | 주문 실패 |
| 10 | 비활성 상품 주문 | 주문 실패 |
| 11 | 삭제 상품 주문 | 주문 실패 |
| 12 | 존재하지 않는 상품 ID 주문 | 주문 실패 |
| 13 | 주문 실패 시 재고 차감 여부 확인 | 재고 차감되지 않아야 함 |
| 14 | 주문 실패 시 매출 반영 여부 확인 | 매출 반영되지 않아야 함 |
| 15 | 주문 성공 시 `orders.order_items` 확인 | 서버 DB 기준 상품명/가격/수량으로 저장되어야 함 |
| 16 | 주문 성공 시 `orders.total_amount` 확인 | 서버 재계산 금액이어야 함 |

## 17. 최종 목표

이번 수정 후에는 최소한 아래 조건을 만족해야 한다.

```text
프론트 total_amount를 그대로 믿지 않는다.
프론트 order_items.price를 그대로 믿지 않는다.
서버가 productId 기준으로 DB 상품 가격을 다시 조회한다.
서버가 상품 합계, 배송비, 최종 주문금액을 다시 계산한다.
서버가 품절/비활성/삭제 상품 주문을 막는다.
서버가 재고보다 많은 수량 주문을 막는다.
재고 부족 주문이 성공하지 않는다.
주문 실패 시 재고와 매출이 변경되지 않는다.
orders.total_amount는 서버 재계산 금액만 저장한다.
orders.order_items는 서버 DB 기준으로 재구성한 상품 목록만 저장한다.
```

핵심은 이것이다.

```text
고객 브라우저에서 온 가격과 총액은 절대 신뢰하지 않는다.
주문 금액과 재고 판단은 반드시 서버 DB 기준으로 한다.
```

## 18. 작업 시 주의사항

이번 작업은 실제 PG 연동 전 보안 보강 1단계이다.

바로 PG 결제, 환불, `payments` 테이블, `refunds` 테이블까지 확장하지 말고, 먼저 주문 생성 API의 금액 검증과 재고 검증을 안정화한다.

기존 UI와 주문 흐름은 최대한 유지하되, 서버에서 프론트 금액을 신뢰하지 않도록 방어한다.

수정 후에는 반드시 테스트 결과를 보고한다.
